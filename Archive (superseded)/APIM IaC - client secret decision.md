# APIM client secret — how do we generate, store and use it?

> [!warning] Superseded — read [[D1 - The developer portal sign-in secret]] instead
> This was the working analysis. The decision itself, and the answer that shipped, live in **D1**.
>
> **What was decided (2026-08-13):** the **APIM component creates the secret itself** on Core's app
> registration, and replaces it automatically every 30 days. No human minting, no Key Vault, no
> renewal diary.
>
> Two things in the analysis below turned out to be wrong, and both are corrected in D1:
> - **"APIM cannot write to Core's app registration"** — it can. That restriction applies to redirect
>   URIs, which are authoritative, not to passwords. `Spoke/AiAgent` already adds two passwords to one
>   registration and already writes to Core's.
> - **"Sub-question 3 — who renews it"** — nobody. It renews itself as part of the APIM deploy. The
>   only residual risk is an environment left undeployed for over a year.
>
> Everything below is preserved because the trade-offs are still the clearest write-up of *why* the
> options were weighed the way they were.

> Written up after the 2026-08-05 meeting.
> **This is a decision document, not a proposal.** It states the problem, sets out the options with
> honest trade-offs, and flags what needs answering before any of it gets built.

---

## The question, in one sentence

> **When we stand up APIM for a customer, who creates the client secret that lets APIM sign users into its developer portal, where is it kept, and who renews it before it expires?**

Three sub-questions sit underneath that, and they can be answered independently:

1. **Which app registration** does the secret belong to — Core's, or one APIM owns?
2. **How does the secret get created** — generated by automation, or by a human in the portal?
3. **Where does it live afterwards**, and who is responsible when it expires?

---

## Why this is a problem at all

The setup guide's **Phase 4C** says, in effect: *create a client secret in one part of the Azure
portal, copy the value, paste it into another part.*

That instruction is fine for a human. It does not survive automation, for three reasons:

- **Automation has nothing to copy from.** There is no portal session, no clipboard, no human.
- **Azure only shows a secret value once.** After creation it is unreadable — even to the person who  made it. So "just read it back later" is not available.
- **It expires.** We set 12 months. Every customer instance would need someone tracking renewal, and the failure mode is silent: portal sign-in simply stops working one day.

### What we are doing today (and why it cannot ship)

The spike reads the value from an environment variable, `APIM_IDP_CLIENT_SECRET`, which a human sets before running the deploy. It is wrapped in `pulumi.Output.secret()` at both use sites, so **it does not leak into logs or state** — that part is correct.

The problem is not safety, it is **provenance and operability**:

- Nothing in `Products/Pipelines/` supplies that variable, so a pipeline deploy fails at program
  evaluation with a `ValueError` — **before Pulumi does anything at all**. That failure is invisible
  until someone tries it.
- It currently reuses **Core's** client secret for a second purpose. Rotating Core's secret would
  silently break developer-portal sign-in with no obvious connection between cause and effect.

Both points were raised independently in Richard's IaC review, marked **Major**.

## What the codebase already does

There are **two established patterns** in the repo, and they solve different problems. Worth being
precise about which one applies, because they look similar.

### Pattern A — generate and store in Key Vault

`Modules/ServicePrincipal/Infra/service_principal.py`

```python
secret = azuread.ApplicationPassword(f"{app_reg._name}-password", application_id=app_reg.id)

add_secret(
    resource_name="intial_secret",
    secret_name=self.service_principal.client_id,
    secret_value=secret.value,
    vault_name=env.environment_components.service_principal.key_vault_name,
    ...
)
```

Automation **generates** the secret and **persists it to Key Vault**. Nobody types anything.
Reading it back later is supported through `safe_get_secret()` and `fetch_secret_after_policy()` in
`Modules/KeyVault/key_vault_interface.py`.

**Use this when** something outside the deployment needs the value later — a human, a support
process, another system, a different Pulumi program.

### Pattern B — generate and consume in the same run

`Spoke/AiAgent/infra/ai_agent_component.py`

```python
self.bot_oauth_secret = azuread.ApplicationPassword(
    "bot-oauth-client-secret",
    application_id=self.bot_app_registration.id,
    end_date_relative="8760h",  # Secret valid for ~1 year
    ...
)
```

The value flows straight into the resource that needs it, inside the same program. It is **never
stored**, because nothing outside the deployment needs to read it.

**Use this when** the only consumer is another resource in the same deployment.

### Which one fits APIM?

**Pattern B, on the face of it.** The only consumer of this secret is the APIM identity provider,
which we create in the same Pulumi program. Nothing external needs to read it, so storing it in Key
Vault would be storing it for no reader.

> [!warning] But there is a catch, and it is the whole difficulty
> Pattern B works cleanly in AiAgent because AiAgent **creates its own app registration** and then
> makes a password on it — one component, one owner, no argument.
>
> APIM does not own an app registration. It **borrows Core's**, which the `Auth` component owns.
> So APIM generating a password means **one component creating credentials on another component's app registration** — and we already know from Phase 4A that two components writing to the same app registration causes real problems.

That is the actual decision. It is not "Key Vault or environment variable" — it is **who owns the
credential**.

---

## The options

### Option 1 — Auth generates the secret and stores it in Key Vault

Auth already owns Core's app registration. It creates the password alongside the redirect URIs,
behind the same `apim_enabled` flag, and writes it to Key Vault. APIM reads it back at deploy time.

| Pros | Cons |
| --- | --- |
| Single, clear owner of the app registration | Two deployments must run in the right order — Auth before APIM |
| Reuses the existing `apim_enabled` flag; no new coupling concept | Auth takes on responsibility for something it does not use |
| Key Vault read-back is an established, working pattern | Needs a Key Vault naming convention agreed for this |
| Renewal is one component's job, in one place | Slightly more machinery than Pattern B |

### Option 2 — APIM generates the secret on Core's app registration

APIM creates the password itself, against a registration it does not own, and consumes it in-run
(Pattern B).

| Pros | Cons |
| --- | --- |
| Simplest code — no Key Vault, no cross-deployment ordering | **Two components writing credentials to one app registration** — the exact class of problem that forced the redirect-URI rework |
| Secret never persisted anywhere | Ownership becomes genuinely unclear |
| Matches AiAgent's shape | Deleting the APIM component would remove a credential on Core's registration |

### Option 3 — APIM gets its own app registration

APIM owns its identity outright: its own registration, its own secret, Pattern B throughout.

| Pros | Cons |
| --- | --- |
| Cleanest ownership — no shared writes at all | Diverges from the setup guide, which explicitly reuses Core's |
| Matches AiAgent exactly | **May not work.** A sign-in token is stamped with whichever identity requested it, so Core would likely reject a token from an APIM-owned registration — see G9 |
| Rotating Core's secret cannot break the portal | Needs Richard's recommended token spike (`aud` / `iss` / `scp`) to confirm either way |
| Richard listed it as a live option (his "Option 2") | Largest change |

### Option 4 — a human creates it once, stored centrally

Status quo, made official: someone mints the secret in the portal and puts it in Key Vault by hand.

| Pros | Cons |
| --- | --- |
| Works today with almost no code | A manual step per customer, at 100+ customers |
| No cross-component writes | Renewal is a human process with a silent failure mode |
| | Runs against the whole point of automating the runbook |

---

## Where this points

**Option 1 looks strongest**, on the evidence we have:

- It keeps a single owner for Core's app registration, which is the constraint that has already bitten us once.
- It reuses machinery that exists and works — `azuread.ApplicationPassword`, `add_secret()`,
  `safe_get_secret()`, and the `apim_enabled` flag.
- It does not depend on the unresolved token question, unlike Option 3.

**Option 3 may be better long-term** and should not be ruled out — but it is blocked behind the token spike Richard recommended. If that spike shows an APIM-owned registration produces a token Core accepts, Option 3 becomes the cleaner answer and Option 1 becomes an interim step.

**Option 2 should probably be rejected outright.** It has the same ownership problem as the redirect
URIs, which we have already paid for once.

## ⏸️ Parked — and Sam's counter-proposal (2026-08-07)

> [!warning] This changes the shape of the answer. Do not build Option 1 yet.

### Status

**Parked pending a dedicated auth meeting.** Sam Clifford's steer on the 2026-08-07 call was to
*"revisit your auth stuff as a whole"* rather than settle the secret in isolation. Grant's decision
is to leave auth alone for now and get agreement in a proper session.

### Sam's framing — auth is two separate problems

Something we'd been conflating. On the call he split it:

1. **User auth** — how people and systems actually call the API. Four distinct audiences: a
   customer's **automated integration script**; a **developer at a customer** exploring the API by
   hand; **machine-to-machine**; and **APIM → Core** itself. *He suggested discussing this one
   first.*
2. **Management-plane access control** — who can administer APIM, see secrets, change policies.

This document only addresses a slice of (1). That's worth knowing before treating it as the auth
decision.

### Sam's Slack follow-up, four minutes after the call

> *"Auth component being updated to read a feature flag to conditionally add a redirect URI. We've
> done work on AiAgent to make the core app reg composable… Taking a similar approach here would be
> my preference. So, rather than having Auth component need to have an awareness of wider
> components, let the components decide if they need to extend any external components they relate
> to."*

Then, four minutes later:

> *"Taking a look at `ApplicationRedirectUris`, it might not be possible. Worth trying out anyway."*

### What this means

**It inverts the ownership argument this document is built on.**

| | Today (Phase 4A, and Option 1 here) | Sam's preference |
| --- | --- | --- |
| Who knows APIM exists? | **Auth** — it carries `apim_enabled` and builds APIM's redirect URIs | **APIM** — it extends Core's app registration itself |
| Direction of the dependency | Auth reaches outwards to every component that might need a URI | Each component reaches inwards to the registration it needs to extend |
| Precedent | None — we invented it for Phase 4A | **AiAgent**, done recently, same problem |

The argument in *"Where this points"* above — that Option 1 wins because it *"keeps a single owner
for Core's app registration"* — is the argument Sam is pushing against. He's not disputing that
single ownership matters; he's saying the way to get it is a **composable registration** that
components extend, not a central component that knows about all of them.

**If a composable app registration works, Option 2 stops being the thing we rejected.** Option 2 is
currently written off because *"it has the same ownership problem as the redirect URIs, which we
have already paid for once"* — but that ownership problem is exactly what the AiAgent pattern
exists to solve.

### The caveat, in his own words

`ApplicationRedirectUris` **might not support it**. Azure AD's Pulumi provider has a history of
partial support for the "extend an existing resource" pattern, and Sam checked and wasn't sure.
So this is a preference with an unproven mechanism, not a decision.

### What to do about it

1. **Don't act on it yet** — Phase 4A works and is deployed.
2. **Look at the AiAgent implementation** before the auth meeting, so we arrive knowing whether the
   pattern actually transfers.
3. **Spike `ApplicationRedirectUris`** — Sam's *"worth trying out anyway"* is the cheapest way to
   settle it. Half a day.
4. **Take the whole auth picture to the meeting**, not just the secret. Sam's split above is a good
   agenda.

### Related, from the same call

- **Nothing rotates these secrets today.** 1-year expiry, no owner. Two options discussed: an
  automated refresh task that adds the secret ID to a blob store (**rotates only** — doesn't apply
  the new value), or **the AI Agent approach Vinny built recently, which rotates *and* applies it**.
  Sam: *"that would get my vote."* Direct answer to the *"who owns renewal"* question below.
- Sam suggested checking whether a **secretless approach** exists at all. His own quick look found
  nothing, but it's worth a proper search before building secret plumbing.
- ⚠️ **Sam noticed the secret in APIM is not obfuscated** — readable in the portal by anyone with
  access. Feeds the management-plane half of the problem; a read-only developer group may be needed.

## Field evidence — the interim workaround is already hurting (2026-08-07)

While this decision is parked, the spike runs on a stopgap: the client secret is read from an
**`APIM_IDP_CLIENT_SECRET` environment variable**, set by hand in the dev container. Phases 5–8 have
now been built and deployed on top of that stopgap, and it has produced concrete evidence worth
recording — because it is a small preview of what the unsolved version looks like in production.

**What actually goes wrong:**

- The variable **does not survive a new terminal.** Every fresh dev-container shell starts without
  it, and the deploy fails until it's re-exported.
- **The VS Code debugger inherits the environment of whichever terminal launched it**, so a debug run
  can fail while an identical run from another terminal succeeds. The failure gives no hint that the
  environment is the difference.
- It is **the only manual step left in the entire component.** Phases 1–8 are otherwise fully
  automated: the service, policies, HMAC secret, product, API, OpenAPI spec and diagnostics all build
  from nothing without a human touching the portal. One env var is the single thing standing between
  the spike and a clean end-to-end run.

**Why this belongs in this document:**

1. It directly contradicts the standing **automate-everything** rule in
   [[APIM IaC - working rules for implementation]]. If a step needs a human, the default answer is
   that the IaC should do it — and this is the one step that still doesn't.
2. It's a **scale argument, not a convenience one.** A missing env var is a mild irritation for one
   engineer on one sandbox. The same class of problem — *"the secret has to get from where it's
   created to where it's used, and nothing guarantees it does"* — is precisely what Options 1–4
   above are trying to solve, at 100+ customer instances where nobody is watching a terminal.
3. It shows the failure mode is **silent and misattributed.** The deploy doesn't say *"your secret is
   missing"*; it fails somewhere downstream. At customer scale that becomes a support ticket about
   portal sign-in, not about a secret.

> [!warning] Do not let the stopgap become the answer
> The env var works well enough that it could quietly persist. It must not. It has no rotation, no
> owner, no audit trail, and no story for a pipeline run — every weakness this decision exists to
> fix, plus a new one: it isn't written down anywhere a new starter would find it.

## What needs answering before we build

### For Richard / Infra-Platform
- [ ] Is **Option 1** the right shape, or is there a Dayshape pattern for cross-component secrets we
      have not found?
- [ ] Which **Key Vault** should hold it — the spoke's, or a shared one? What naming convention?
- [ ] How do we handle the **ordering dependency** (Auth before APIM)? Does the orchestrator already
      guarantee this, or does APIM need to fail gracefully when the secret is absent?
- [ ] Does APIM read the secret via **Key Vault directly**, or does it get a managed identity and use
      APIM's **native Key Vault integration for Named Values**?
      **→ Answered by Phase 5.** A system-assigned managed identity on the APIM service, granted Key
      Vault Secrets User, with a `key_vault`-backed Named Value. See
      [[APIM IaC - HMAC signing secret decision (phase 5)]]. Once that is deployed and proven, this becomes a
      live option for the client secret too and Option 1 below should be re-examined.

### For Product
- [ ] Who owns **renewal** at 100+ customer instances, and what tells us it is about to expire?
      **→ Partially answered 2026-08-07.** Nothing does today. Sam's preference is the **AI Agent
      rotation approach Vinny built**, which rotates *and* applies the new value — unlike the
      blob-store refresh task, which only rotates.
- [ ] Is a **12-month** expiry right, or should it be shorter with automated rotation?
- [ ] What is the **acceptable failure mode** if it does expire — portal sign-in stops, which is
      customer-visible. Is that a Sev-2?

### To investigate ourselves
- [ ] **Does the AiAgent composable app-registration pattern transfer to APIM?** Read the AiAgent
      implementation before the auth meeting. *(Added 2026-08-07 — Sam's preferred direction.)*
- [ ] **Spike `ApplicationRedirectUris`** — Sam thinks it may not support extending an existing
      registration, but said it's *"worth trying out anyway."* Half a day, settles the question
      above.
- [ ] **Is there a secretless approach?** Sam looked briefly and found nothing, but suggested a
      proper search before we build secret plumbing at all.
- [ ] Does APIM's identity provider `clientSecret` accept a **Named Value reference**, or does it need
      the literal string? This materially changes the design and is a docs question, not a debate.
- [ ] Confirm whether **`safe_get_secret()`** works across separate Pulumi programs, or only within one.
