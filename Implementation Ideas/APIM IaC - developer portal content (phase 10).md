# APIM IaC — the developer portal content: where it lives and how it gets to customers

> [!warning] Superseded by the code
> Phase 10 is **built and proven end to end against real Azure**. This document previously said "draft — questions in Part 8 need answering before implementation"; those questions were answered and the work was done. One defect found in live testing is tracked as **G28**.
>
> **Where this document and the code disagree, the code is right.** Kept for the reasoning behind
> the decisions, not as a description of how things behave today.

> [!abstract] The whole thing in five sentences
> Every customer's API documentation site needs pages, styling and images. None of that is
> generated by us — it is **hand-designed in a browser on a single sandbox instance**, and
> then copied onto each customer's site. Our technical authors write the documentation there,
> so that sandbox is a **live working environment, not a leftover**. Phase 10 of the setup
> guide is the copy step, and today it is a person running a script on their laptop. This
> document proposes how to automate it, and asks the questions I cannot answer alone.

Parts 1–6 explain the problem from scratch (written so it can be handed to a PO).
**Part 7 is the proposed approach. Part 8 is the list of decisions needed.**

---

## Part 1 — What the developer portal actually is

When a customer wants to connect their own systems to Dayshape, they need documentation:
what they can ask for, how to authenticate, what comes back.

APIM gives every customer a **developer portal** — a small documentation website that sits
alongside their Dayshape instance. It has two kinds of content on it:

| Content | Where it comes from |
| --- | --- |
| The list of API endpoints | Generated automatically from the OpenAPI file (that's Phase 7, already designed) |
| Introduction, Authentication, "Dayshape Objects", the styling and images | **Hand-written and hand-designed by people** |

Phase 7 solved the first row. **This document is about the second row.**

---

## Part 2 — What Phase 10 does today

The written pages and the visual design are not generated from anything. Somebody sat down
and designed them, and they now need to appear on every customer's portal.

The setup guide's Phase 10 is that copy step. Today it is four manual actions:

1. Take a backup of the customer's current portal
2. Wipe the customer's portal content
3. Take a copy of the master content
4. Load that copy onto the customer's portal

Voodoo Park have already wrapped these four steps into a single command
(`Dayshape\Dayshape\Tools\ApimContentClone\`). It is a decent piece of work — it has a
practice mode, it refuses to run if you accidentally point it at the master, and it keeps a
record of each run. **We are not being asked to write the copying logic. It exists.**

The question is purely how to make it happen automatically as part of a deployment, instead
of a person remembering to do it.

> [!info] Worth knowing: the wipe is less alarming than it sounds
> Step 2 removes the *draft* content only. The customer's live portal keeps serving the old
> version throughout, and only switches over when the new content is published at the end.
> Customers do not see a broken or empty site while this runs.

---

## Part 3 — Where the master content lives, and why

The master copy lives on an APIM instance called **vprk2**, in Dayshape's sandbox
subscription. Every customer's portal is a copy of that one.

That sounds like an accident. It isn't. There are two reasons, and the second one is the
important one.

**Reason one: there is no file to edit.** The portal is designed through a drag-and-drop
visual editor in the browser. There is no document or code file that represents the design —
the instance *is* the design tool. Laszlo Szegedi of Voodoo Park confirmed this is the
intended way of working, in Slack on 17 June 2026:

> *"if anyone wants to make any changes to the styling or static content, they need to do it
> on the vprk2 apim instance and then run the content copy scripts"*

**Reason two: our technical authors work there.** On 14 July 2026 Jonathan Lozinski asked for
edit access on that instance for **Sarah Dimmock and Sinead Donnelly**, so they could write
the customer-facing documentation before it was copied out to customer sites.

That second point changes how we should think about Phase 10 entirely:

> [!important] Phase 10 is a publishing pipeline, not a one-off setup step
> It is the route by which our technical authors' work reaches customers. It will run again
> every time the documentation is updated — not just when a new customer is onboarded. Any
> change we make to it changes how the authoring team works, so they are stakeholders.

## Part 4 — Why automating it as-is turns out to be awkward

I initially assumed we could simply run Voodoo Park's script from our deployment process.
Three things get in the way.

### 4.1 — Our deployment container doesn't have the tools

The script needs five things: Git, Node.js, npm, the Azure CLI and PowerShell.

Our deployment container has three of them. Node and npm were deliberately left out of the
production image — they exist only in the *developer* variant, added for AI tooling.
PowerShell isn't there at all.

So running the script as-is means adding tools to an image shared by **every deployment
across the company**, for the benefit of one component. That's a conversation with the
platform team, not a decision we can take on our own.

### 4.2 — Every customer deployment would reach into a sandbox

If each customer deployment copies live from vprk2, then **every customer deployment depends
on a sandbox instance staying alive** — in a different subscription, on infrastructure nobody
treats as production.

There is a sharper version of this risk. The copying tool wipes the customer's portal, then
loads what it read from the master. If that read were incomplete — a network blip, a
throttled response — the tool would cheerfully wipe pages and not put them back, and report
success. That's a quiet way to lose a customer's documentation.

### 4.3 — The safety net evaporates

The tool backs up the customer's portal before wiping it, which is the right instinct. But it
writes that backup next to itself — on a container that is destroyed when the job finishes.
So the backup exists for about ninety seconds and then disappears. The only rollback path
goes with it.

---

### 4.4 — Microsoft says this copy is not supported on the tier we run

This one surfaced late and is the most awkward of the four, so it needs stating plainly.

Microsoft publishes guidance on automating developer portal deployments — the process in our
setup guide is a wrapper around Microsoft's own scripts, which is reassuring. But that same
guidance carries a restriction:

> *"Using the script to migrate developer portal content between an API Management instance in a
> classic tier (for example, Standard) and an instance in a v2 tier (for example, Standard v2)
> isn't currently supported. Migration of portal content between instances in the v2 tiers is
> also not supported."*
>
> — [Automate developer portal deployments](https://learn.microsoft.com/en-us/azure/api-management/automate-portal-deployments),
> Microsoft Learn, updated 1 October 2025

That page is also labelled **"APPLIES TO: Developer | Basic | Standard | Premium"** — the four older
tiers. `BasicV2` isn't one of them, so the guidance doesn't claim to cover our setup in the first place.

Both ends of our copy are v2 tiers:

| Instance | Tier |
| --- | --- |
| `vprk2-sbx-spk-apim` — the master we copy from | **BasicV2** |
| Every customer instance we deploy | **BasicV2** |

So the second sentence lands squarely on us. The copy we do today, by hand, for live customers, is
on a path Microsoft describes as unsupported.

**In practice it works.** A colleague ran the clone against a customer environment in July and
confirmed it succeeded, and APIM is live for customers now. Unsupported is not the same as broken —
it means Microsoft makes no promise it will keep working and will not help if it stops.

The risk is not that it fails tomorrow. It is that automating it changes the shape of the exposure.
Today a person runs it now and again and looks at the result. Automated, it runs unattended for
every customer, so a change on Microsoft's side would reach everyone before anyone noticed.

Worth separating two things Microsoft says, because they are easy to run together:

| What | Microsoft's position |
| --- | --- |
| The underlying content management **API** | **Supported** — documented as the way to import and export portal content |
| Their packaged **migration script** between v2 instances | **Not supported** |
| **ARM templates** for portal content | **Not supported** |

Both positions come from Microsoft's own pages —
[Automate developer portal deployments](https://learn.microsoft.com/en-us/azure/api-management/automate-portal-deployments)
and the [Developer portal FAQ](https://learn.microsoft.com/en-us/azure/api-management/developer-portal-faq).

The operations are supported; the packaged migration path is not. That pushes us towards driving the
content API ourselves rather than shelling out to Microsoft's script — which is Question 1 below.

One more line from the same source is worth knowing: **APIM's own backup and restore does not cover
developer portal content.** So the only copy of a customer's portal is the one we take. That makes
4.3 above more serious, not less.

---

### 4.5 — The same documentation points at a way through

Having found the restriction, I went back through Microsoft's pages looking for what they *do*
recommend for our tier. There is a clear answer, and it hinges on something easy to miss: **the two
pages apply to different tiers.**

| Page | Applies to |
| --- | --- |
| [Automate developer portal deployments](https://learn.microsoft.com/en-us/azure/api-management/automate-portal-deployments) — where the "not supported" note lives | Developer, Basic, Standard, Premium — **the classic tiers only** |
| [Developer portal FAQ](https://learn.microsoft.com/en-us/azure/api-management/developer-portal-faq) | Developer, Basic, **Basic v2**, Standard, Standard v2, Premium, Premium v2 — **includes us** |

So the page telling us the migration script is unsupported is written for tiers we do not run. The
page that *does* cover BasicV2 points somewhere else — at the content item API:

> *"Optionally, delete the Sign up page. Currently, you use the **contentItem REST APIs** to list and
> delete this page."*
> — Developer portal FAQ, on a page that explicitly covers Basic v2

That API is fully released — [Content Item](https://learn.microsoft.com/en-us/rest/api/apimanagement/content-item),
API version `2024-05-01` — and offers everything the job needs:

| Operation | What it gives us |
| --- | --- |
| **List By Service** | Enumerate every page on the master |
| **Get** | Read one page's content |
| **Create Or Update** | Write a page onto a customer instance |
| **Delete** | Remove a page that no longer exists on the master |
| **Get Entity Tag** | Detect whether a page has actually changed |

This is the same API that Pulumi's `ContentItem` resource sits on top of — which is the Option B
route in Question 1. **Option B is no longer just "our own code to write and maintain". It is the
route Microsoft points our tier at.**

Two further points from the same FAQ that are worth having:

- **The cleanup script is still recommended** on that v2-applicable page, so parts of Microsoft's
  script toolkit are fine for v2. It is specifically the *migration* path that is not.
- **Custom widgets and the custom HTML widget are not available on the v2 tiers at all.** Since both
  vprk2 and every customer instance are BasicV2, the master content can only be built from standard
  built-in widgets. There is no exotic custom content that could fail to transfer — which lowers the
  risk of whatever approach we choose. Worth confirming by looking at what is actually on vprk2.

One honest caveat: the FAQ also answers **"No"** to *"Does the portal support Azure Resource Manager
templates?"*. Calling the content item REST API directly is not the same thing as an ARM template
deployment, and Pulumi works through the former. But that "No" may reflect a real difficulty in
expressing portal content declaratively — pages reference layouts, layouts reference styling, and
ordering matters. **A dry run would settle it.** I would not treat Option B as proven until we have
read the master content once and looked at its shape.

### 4.6 — The gap in Option B: media

There is a second, larger caveat, and it needs stating before anyone treats Option B as the obvious
answer. Microsoft's description of their script is *"captures the portal content **and media**"* and
*"uploads the portal content **and media**"*. Portal content and media are two different things:

| Thing | What it is | Can Pulumi do it? |
| --- | --- | --- |
| **Content items** | Pages, layouts, navigation, styling configuration | **Yes** — `ContentItem` and `ContentType` both exist in `azure-native` |
| **Media** | Images, logos, diagrams, uploaded files | **No** — there is nothing media-related in `azure-native` at all |

Uploading media needs a short-lived storage token from a `listMediaContentSecrets` operation, and
that operation is absent from the Azure provider we use. So Option B as described covers the pages
but not the pictures on them.

That does not kill it. There are three ways it could still work, and we do not yet know which applies:

1. **There is very little media.** If the portal is mostly text with a logo, we could handle the few
   files another way, or accept setting them once by hand.
2. **We call the media operation directly.** It exists in the REST API even though Pulumi does not
   wrap it. That is more of our own code, and closer to the line on our "no direct Azure API writes"
   rule, so it would need agreeing first.
3. **A hybrid.** Pulumi for the pages, Microsoft's script for the media. Probably the worst of both.

**This is the single most important unknown in Phase 10**, and one read-only capture of vprk2 answers
it outright — it tells us how many content items there are and how much media sits alongside them.
Until then, Option A is the only route we know handles everything, because Microsoft built it to.

## Part 5 — We have already solved this problem twice

Before proposing anything new, I checked whether this shape of problem is already handled
elsewhere in our infrastructure code. It is — **twice** — and one of them is our own work.

### 5.1 — Language packs

The LanguagePack component ships translated content into customer environments. It doesn't
read from a live source. Instead:

- Content is published as a **versioned bundle** to a central store (`dsartifactrepo`)
- Each customer deployment pulls **the version matching the release being deployed**
- Access uses a short-lived read token, so no standing permissions are needed

### 5.2 — Our own OpenAPI work (Phase 7)

We built exactly the same thing for the API documentation file: published to the same central
store, versioned the same way, with a local path for development and a published path for
real deployments.

> [!success] This pattern already has senior blessing
> In the review on 2026-08-07, **Sam Clifford confirmed the language pack publish is the model
> to copy** — he wrote it. He also framed it as a step towards decoupling infrastructure
> deploys from application deploys. Phase 10 is the same shape of problem.

---

## Part 6 — What that pattern does for Phase 10

Applying it here means splitting the work in two:

**At release time, once:** capture the master content from vprk2 and publish it as a versioned
bundle to the central store.

**At deployment time, per customer:** pull the bundle for the relevant version and apply it to
that customer's portal.

That one change resolves most of Part 4:

| Problem | Resolved how |
| --- | --- |
| Deployment container lacks Node and PowerShell | The capture runs once, on a standard build agent that already has them. The shared image may not need to change at all. |
| Every deployment depends on a sandbox | No customer deployment ever touches vprk2. |
| A partial read could delete customer pages | You cannot half-read a published bundle. |
| Backup disappears with the container | Rollback becomes "deploy the previous version". |
| Downloading tooling from the internet mid-deployment | Moves to the release-time job. |
| "Only run it when the master has changed" | Becomes a comparison against the last published snapshot. |

It also gives us something we do not have today: **a record of what documentation each
customer actually received.**

## Part 7 — Proposed approach

1. **A capture job.** Reads the master content from vprk2 and publishes it as a versioned
   bundle. Runs on a standard build agent. Mirrors how we already publish the OpenAPI file.
   **When this runs is not obvious — see 7.1.**
2. **A resolver in our component.** Fetches the right bundle for the deployment. This is very
   close to a copy of the Phase 7 OpenAPI resolver.
3. **An apply step** that puts the content onto the customer's portal. **See question 1 below —
   this is the one genuinely open decision.**
4. **Prove it manually first** against a throwaway instance, before writing any code.

### 7.1 — The versioning problem, stated honestly

The OpenAPI file has a real version because it is **built from committed code**. Ask for the
file for release 26.5 and you get exactly one answer, forever. The same is true of language
packs — they are built from files in the repository.

**The portal content has none of that.** vprk2 is a live instance that people edit in a
browser. There is no version, no history, no commit, and no way to ask "what did it look like
last month". Whatever is on it right now is the only state that exists.

So when I said "publish it as a versioned bundle", I was describing something we would have to
*create*, not something we could read off. That is worth being clear about, because it has a
consequence that matters more than the labelling:

> [!warning] There is no concept of "finished"
> With code, "ready to ship" is a commit. With vprk2, there is no equivalent. If a capture runs
> while Sarah is halfway through rewriting a page, we would publish the half-finished page — and
> given the answer to Question 3, it would then propagate to every customer on their next
> orchestrator run.
>
> This is not a flaw in the proposal. It is a flaw in the current arrangement that automation
> would expose. Today a person captures the content when they know it is ready. Automation
> removes that judgement unless we replace it with something.

### 7.2 — What I think we should do about it

Rather than tying the capture to the release cycle, **make publishing a deliberate act**.

- The authors work on vprk2 exactly as they do now.
- When they consider the documentation ready, **a capture is triggered** — by them, or by us
  on their say-so.
- That capture is published as a new numbered snapshot.
- Customer deployments pick up the most recent published snapshot.

This has three things going for it. It gives the authors an explicit "this is ready" moment,
which is the thing that currently doesn't exist. It decouples documentation from the release
cycle, so a typo fix doesn't have to wait for a release. And it gives us the record of what
shipped that we don't have today.

The version number itself can simply be the date and time of capture. It isn't derived from
anything meaningful, and pretending otherwise would be dishonest — but it does give us
"customer X received snapshot 2026-08-10-1430", which is more than we can say today.

It is also worth recording a fingerprint of each capture, so we can tell whether the content
actually changed between two snapshots. That makes it cheap to skip work when nothing has moved.

**Alternative if that's too much process:** tie the capture to the release cut, accept that
documentation only reaches customers at release boundaries, and accept the risk of catching an
edit mid-flight. Simpler, but it hands the authoring team a worse deal than they have now.

## Part 8 — Questions I need answered

> [!question] Question 1 — How do we apply the content to the customer's portal?
> This is the main decision and everything else follows from it.
>
> **Option A — use Voodoo Park's script.** Faithful to the guide, no new logic from us. But it
> needs Node added to the deployment container, and it works by wiping and reloading.
>
> **Option B — apply it ourselves, page by page.** Pulumi works out what actually changed and
> only touches that. No new tools in the deployment container, no wipe. But it is our code to
> write and maintain, and it departs from the written guide.
>
> My honest view is that Option B looks stronger now that the bundle removes the risky parts —
> mainly because it avoids changing an image shared by every deployment in the company. **The
> support position in 4.4 and 4.5 makes that clearer still:** the page carrying the "not supported"
> note is written for the classic tiers only, while the page that does cover BasicV2 points at the
> content item API — which is exactly what Option B uses. So Option B is not a departure from
> Microsoft's guidance; on our tier it is closer to it than Option A is.
>
> I would still not call it proven. The same FAQ says ARM templates aren't supported for portal
> content, and a declarative model may struggle with how pages, layouts and styling reference each
> other. **A single read-only capture of the master would tell us**, and I'd want that done before
> committing either way.

> [!question] Question 2 — What does a "version" of the portal content even mean?
> This is the weak point in the proposal and it needs thinking through properly. See Part 7.1
> below — the short version is that **the master content has no version and no concept of
> "finished"**, so we have to invent both. My proposal is that publishing becomes a deliberate
> act by the authoring team rather than something tied to the release cycle, but that is a
> proposal, not a conclusion.

> [!done] Question 3 — Answered
> Documentation updates **do** reach existing customers, when the orchestrator next runs for
> them. That is the intended behaviour.
>
> This makes Question 2 more pressing rather than less. If an update propagates to every
> customer automatically, then a half-finished edit propagates to every customer automatically
> too. Something has to distinguish "ready" from "in progress", and today nothing does.

> [!question] Question 4 — Are we content to keep vprk2 as the master?
> Keeping it means the authors keep the visual editor they already use, which is a real benefit.
> It also means a sandbox instance stays a permanent dependency. If we keep it, it must be named
> explicitly in our documentation so nobody deletes it during a tidy-up. Note that when Jonathan
> asked about access in July, **Voodoo Park's own engineer went to the wrong instance** — the
> name gives no clue what depends on it.

> [!question] Question 5 — Who owns publishing?
> Voodoo Park's tool can publish the portal at the end of its run. We already built publishing
> in Phase 9. Two things doing the same job will eventually collide, so one of them should own it.

> [!question] Question 6 — Is the editor race acceptable?
> The guide warns that opening the portal editor while a copy is running corrupts the import.
> Done by hand, that's easy to avoid. Automated, one of our authors browsing the portal at the
> wrong moment could break a customer's deployment. Do we mitigate this, or document it and
> accept it?

> [!question] Question 7 — Are we comfortable automating a path Microsoft doesn't support?
> See 4.4 and 4.5. Both our master and every customer instance are BasicV2, and Microsoft states
> that portal content migration between v2 instances is not supported. It works today, but
> automating it means it runs unattended everywhere rather than occasionally by hand.
>
> **4.5 gives us a way to sidestep this rather than accept it.** The restriction applies to
> Microsoft's migration *script*; the content item API it points our tier at carries no such
> note. Choosing Option B in Question 1 largely dissolves this question. Choosing Option A means
> consciously accepting it.
>
> Either way I'd suggest asking Microsoft for a written position through our support agreement —
> it costs only time and the answer is useful whichever route we take.

---

## Part 9 — What I'd do next

Run Voodoo Park's tool by hand, once, against a throwaway instance — in practice mode first.
It is low risk and it turns four open questions into facts: whether we can reach the master,
how long a run takes, how large the content is, and whether anything unexpected breaks.

I'd want that done before writing any code.
